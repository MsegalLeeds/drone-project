# Drone build plan

**First flight goal:** a short, pilot-controlled hover with roll and pitch stabilisation, yaw-rate control, and manual throttle. Agree the test site, pilot, hover target, limits and abort conditions with the university team before powered flight. Altitude hold and GPS navigation are later milestones. Use the [bench checklist](todo.md) to record results.

## What already works

The FK743M3-VGT6 board runs C over USB. The blue LED is on PC13, and the double-blink program ran from RAM. Pressing RST restores the original program. On 8 November 2026 a fresh build of the [flight-controller project](../../software/flight-controller/CMakeLists.txt) passed all nine tests on the Mac. It already estimates roll and pitch, controls yaw rate, and computes four motor commands for an X-shaped quadcopter. These results cover the simulator. Real sensor orientation, timing, radio behaviour and propulsion still need bench tests.

## 1. Work now with the Mac, STM32 and USB cable

1. **Make one tilt test portable.** Start with a short sequence of artificial accelerometer and gyro readings in the project's existing units (m/s² and degrees/s). Include level, right side down, and a return to level. Run it on the Mac. Record the expected roll, pitch and four calculated motor commands. Use the signs and corner names in the [existing flight-controller code](../../software/flight-controller/src/control/flight_controller.c).
2. **Run that test on the STM32.** Add a board build capable of linking the existing C modules, startup code, and the maths library. Keep the RAM blink loader as a recovery test. Replay the same samples on the chip with the same time intervals. Leave all four motor pins inactive. Initially use the blue LED to indicate whether the numeric checks pass. Then add a USB serial console to print the numbers on the Mac. The board needs firmware for USB serial in addition to the USB bootloader used for loading code.
3. **Test failures in software.** Start disarmed. Simulate high throttle at startup, missing or stale sensor samples, invalid readings, a late control update, radio loss, and deliberate disarm. Define the intended response for each case on the bench and in flight. Check that a restart or restored radio link cannot arm the aircraft by itself.
4. **Prepare the hardware work on paper.** Mark the front of the frame, the four motor positions, their intended rotation, and the IMU orientation. Turn the signal names in the [existing wiring diagram](../../hardware/wiring/drone-wiring-diagram.pdf) into a pin table for this exact board revision. Check pin functions, timer channels, header labels, voltage levels and clashes with USB, SWD debugging, and storage. Mark unconfirmed pins as open. Choose the onboard microSD socket or the listed external breakout, and map that one. Confirm the radio choice and outstanding parts, including the card, radio batteries, battery strap and first-power current limiter.

**Ready for wiring when:** the STM32 reproduces the Mac's tilt test, invalid inputs have visible fault indications, and the IMU power and signal pins have been verified. The receiver and motor wiring can be mapped while the IMU software is being tested.

## 2. First wiring session: USB power and the motion sensor

5. **Connect only the SparkFun LSM6DSO.** With USB unplugged, prepare the breakout for the planned SPI connection. Check SparkFun's instructions for the default address jumper on the actual breakout. Connect 3.3 V, ground, clock, data in, data out and chip select using the verified table. Add its data-ready signal if used. Inspect continuity, then power up over USB and read register 0x0F. The expected device ID is 0x6C. [SparkFun breakout guide](https://learn.sparkfun.com/tutorials/qwiic-6dof-lsm6dso-breakout-hookup-guide/hardware-overview) · [ST sensor driver](https://github.com/STMicroelectronics/lsm6dso-pid/blob/master/lsm6dso_reg.h)
6. **Replace artificial readings with motion you can measure.** Configure the sensor range and sample rate, convert raw readings into ImuSample units, and measure stationary gyro offsets. Rest the board on each face to check gravity direction and magnitude. Tilt about one marked axis at a time and rotate it by hand. Check roll and pitch direction, yaw-rate sign, update interval and sample age on the Mac. Use the blue LED for a visible tilt test.
7. **Run the real control loop with motors disabled.** Print or log the four named outputs. At nonzero simulated throttle and a level target, lowering the right side should make the controller request more thrust on the right relative to the left. Repeat for pitch and check yaw separately against the chosen rotation map. Interrupt the IMU data and verify the planned fault response.

## 3. Build and test the aircraft with propellers removed

8. **Bring up power before attaching electronics.** Inspect the frame, motor mounts and battery restraint. With the power off, check polarity, continuity, capacitor orientation and the 3S battery power path through the Matek PDB. Check the dedicated 5 V regulator and board's 3.3 V rail using a meter before connecting dependent devices. Use the current limiter for first power-up. Keep the separate 5 V supplies isolated as shown on the diagram. Calibrate the HCS-150A voltage/current readings against measurements. Verify the USB/debug connection cannot backfeed the board.
9. **Make firmware and radio work after a cold start.** Back up the installed program and verify the recovery method before writing persistent flight firmware. Install the tested build, power-cycle without a Mac, and check it starts disarmed. If the planned RadioMaster RP1 V2 and Pocket ELRS are selected, bind them and decode CRSF receiver data. Verify channel order, endpoints, throttle, arm switch and range. Exercise the disarm and link-loss responses with propellers removed.
10. **Integrate logging and remaining equipment separately.** Log sensor samples, estimated angles, radio commands, four motor commands, battery readings, loop timing and fault events to microSD. Read the file back after a run and test a missing card. Fit and test the VIFLY buzzer with its driver. Check the BMP388 pressure trend, Foxeer M10Q outdoor position fix and IST8310 heading independently before using any in a control mode. Manual stabilisation can be developed while those three sensors are being commissioned.
11. **Prove each motor channel.** Confirm which control signal the four 12 A BLHeli ESCs accept. Check the pulses and disarmed output before enabling a motor. With props removed, command the four 2204 motors individually and record corner, rotation and stop behaviour. Repeat the tilt, reset, disarm and radio-loss tests on the assembled aircraft; review the output and timing logs. [Motor direction testing](https://docs.ardupilot.org/copter/docs/connect-escs-and-motors.html)

## 4. Validate propulsion and make the first hover

12. **Measure propulsion under load in the university's guarded test setup.** Check the actual motor, propeller, ESC and 3S battery combination. Record current, thrust, voltage sag and temperature. Compare measurements with component limits, all-up weight and required thrust margin. A props-off spin test cannot establish those quantities. Set initial controller gains, limits and abort conditions using bench evidence. Test stabilisation on a suitable rig before free flight.
13. **Fly a short manual hover and review it.** With an experienced pilot at the agreed site, check battery retention, centre of gravity, propeller orientation and fixings, correct model selection, radio range and disarmed startup. Confirm applicable site and flight requirements. Take off for the agreed short hover, land and disarm. Stop for unexpected roll, pitch, yaw, oscillation or power loss. Inspect the frame and review the log before changing one parameter or expanding the flight envelope.

**First-hover evidence:** the aircraft responds in the expected direction, lands under pilot control, and produces a readable log. Use the team's [requirements](../../docs/requirements.md) to record what was actually achieved. Add altitude hold first and position hold later only after the relevant sensors and loss-of-sensor behaviour have been demonstrated.
